# 需求文档审查

## 适用场景

任何需求类文书(PRD、需求规格说明书、用户故事、功能清单)都应执行本技能。
重点查四类问题:遗漏(该写没写)、矛盾(前后或跨章节冲突)、歧义(存在多种解读)、不可验收(无法转成测试)。

注:本场景只读 txt/md 纯文本;docx/pdf 会被 `read_file` 拦成占位文案(见二进制拦截),若用户给的是后者,应提示其转为文本格式再上传。

## 执行步骤

### 1. 通读并建立章节索引

用 `find_files` / `list_files` 找到文档(示例省略必填参数 `repo_path`,实际调用须带上任务工作区根路径——文书任务通常为上传文件,系统已注入工作区、见任务上下文),
再用 `read_file` 通读(返回带行号,供后续精确定位)。先记下章节结构与需求编号规则(如 `FR-1`、`3.2.1`),
后续所有引用统一按它定位。

### 2. 检查完整性(有没有漏)

用 `search_code` 定位章节标题与编号(如 `^#{1,3}\s`、`FR-\d+`、`验收标准`),对照一份需求应含的要素查缺:
- 背景与目标、范围(做什么 / 明确不做什么)
- 角色与权限、主流程与异常流程
- 功能需求、非功能需求(性能 / 并发 / 安全 / 可用性 / 兼容性)
- 数据与接口、依赖与前置条件
- 验收标准(每条需求是否有可判定的通过条件)

缺哪一类就是一类问题。尤其注意:只有功能需求、完全没有非功能需求与验收标准,是高频缺漏。

### 3. 检查一致性(有没有打架)

用 `search_code` 搜关键名词与情态词(如 `必须|不得|应当|可选`、同一实体的不同写法),逐对确认:
- 同一需求在不同章节结论冲突(一处「必须登录」、另一处「允许匿名」)
- 术语不统一(同一实体多种叫法,或同一个词指代不同实体)
- 编号 / 交叉引用对不上(引用了并不存在的 `FR-7`)
- 分级口径矛盾(标 P0 的需求却写「后续版本实现」)

### 4. 检查可测试可验收(能不能验)

逐条需求判断能否转成明确测试:
- 含不可度量的词而无阈值(`高效`、`快速`、`尽可能`、`友好`)→ 不可验收
- 缺验收标准,或缺边界与异常路径(空值、极值、并发、越权、超时)
- 只写「支持 X」却不写 X 的输入输出与约束边界

建议把「输入→预期输出」或 Given-When-Then 的改写写进修复建议,作为可验收的佐证。

### 5. 检查隐含假设与优先级

- 隐含前提未写明(如「默认用户已登录」「假设上游一定会传某字段」)
- 优先级不清或缺依赖关系(哪条先做、哪条被谁阻塞)

### 6. 输出结果

每个问题在最终总结里给出:
- **位置**:文件:行号(或需求编号)
- **类别**:缺漏 / 矛盾 / 歧义 / 不可验收 / 隐含假设 / 优先级不清
- **严重度**:high(会导致返工或验收争议)、medium(需澄清但可补)、low(表述打磨)
- **证据**:引用原文片段(带行号或需求编号)
- **建议**:缺的补什么、矛盾以哪条为准、歧义列出多种解读并请作者确认、不可验收改成可判定的验收条件

## 避免误报

- 背景 / 愿景 / 市场叙述属非可验收内容,不按「不可测试」报
- 明确指向其他文档的细节(如「UI 以设计稿为准」)不算缺漏
- 需求本身已给出量化阈值或明确验收条件的不报
- 合理分级(P0/P1 有意分批)不算优先级问题

## 避免漏报

- 隐含假设最难发现:留意「默认」「正常情况」「通常」这类措辞背后的前提
- 模糊枚举(「等」「以及其他类似场景」)会让范围失控,要指出
- 只覆盖正常路径、缺异常 / 边界路径,是常见漏报点
- 非功能需求整节缺失常被忽略,要专门对照检查
