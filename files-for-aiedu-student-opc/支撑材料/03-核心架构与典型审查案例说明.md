# 03 · 核心架构与典型审查案例说明

> 面向非技术背景评委：本文尽量用大白话讲清「谁在做事、结果凭什么可信」。专有名词首次出现时附一句通俗解释。

## 一、系统总体架构

### 1. 总体架构图

```text
              ┌───────────────────────────────────────────────────────────┐
              │                      网页前端（Vue 3）                      │
              │  建任务 / 任务详情（主对话流 + 检查助手侧栏）/ 知识点看板 / 设置  │
              └───────────────▲──────────────────────────┬────────────────┘
                              │ 实时事件流（SSE）           │ 常规接口（REST）
              ┌───────────────┴──────────────────────────▼────────────────┐
              │                  后端服务（FastAPI · 单 worker）            │
              │                                                           │
  交付物 ───► │  编排层：把「先产出」与「后台复核」串成一条流水线               │
              │     ├─ 执行层                                                 │
              │     │    ├─ 内置 AI助手（react_agent）                        │
              │     │    └─ 外部命令行智能体：Qoder / DeepSeek Harness / Codex │
              │     ├─ 检查助手：后台独立复核，只审不改                          │
              │     │    ├─ 只读查证（读文件 / 搜代码 / 列目录）                 │
              │     │    ├─ 引用核实（抓取外部链接，防内网穿透）                  │
              │     │    ├─ 证据台账（结论挂靠真实证据，可信度由后端算）           │
              │     │    └─（实验性）沙箱内实际运行验证                          │
              │     └─ 出题与练习服务（生成 → 确认 → 排期 → 判分）                │
              │                                                           │
              │  工具层 / 证据层 / 智能体策略 / 记忆与场景模板                   │
              └───────────────┬───────────────────────────────────────────┘
                              │ 工具调用
              ┌───────────────▼──────────────────────────────────────────┐
              │     容器化沙箱（OpenSandbox）：隔离执行，克隆仓库、跑验证代码    │
              └──────────────────────────────────────────────────────────┘
```

> 一句话读懂：最上面是网页界面；中间是后端，把「干活」和「复查」排成一条流水线；最下面是隔离的容器沙箱——智能体每一步操作都在沙箱里完成，不影响你自己的电脑。

### 2. 核心模块说明

| 模块 | 职责（大白话） | 关键机制 |
|---|---|---|
| **编排层（总调度）** | 把「先产出」和「后台复查」串成一条流水线：AI助手 先跑 1 轮 → 先给出结果并显示任务完成 → 同一个后台流程接着跑检查助手复查 → 再用提炼出的知识点更新结果 | 网页通过一条常开的实时消息通道接收进度，直到最后一步结束才关闭；用户看到「完成」以 AI助手 结束为准，等待时间可预期 |
| **AI助手（执行者）** | 按你写的任务说明实际动手：克隆仓库、读源码、跑静态检查、执行脚本、写出产物 | 内置实现 `react_agent`，采用「想一步 → 调一个工具 → 看结果 → 再想下一步」的循环（业界称 ReAct）；也可换成外部命令行智能体（Qoder / DeepSeek / Codex）。两者经统一接入协议接入，可随时更换，换执行层不改业务主干 |
| **检查助手（复核者）** | 在后台**先核查、只审不改**：回到真实源码逐条比对、抽查外部引用是否可信、必要时实际跑一段验证代码，最后整理「重点与知识点」与「建议追问方向」 | 通过四个结构化的上报入口即时提交：审查计划 / 审查项 / 知识点 / 建议；每条结论挂靠真实证据（源码行 / 验证运行结果 / 抓取到的外部依据），可信度由后端按证据计算，**模型自己不能报数字**；它没有改代码的权限，只有查证的职责 |
| **工具层** | 智能体伸手要用的各种工具，只负责查证与分析 | 读文件、搜代码、按文件名查找、运行静态扫描（Semgrep / lint）、查依赖漏洞、核实外部引用、在沙箱内跑 Python 或发网络请求等 |
| **容器化沙箱（OpenSandbox）** | 所有工具调用都在隔离的容器里执行 | 自建运行镜像（含 git、ripgrep、python3、Node.js）；验证代码在沙箱内真实触发 |
| **出题与练习服务** | 把真实发现变成练习题 | 标记「有出题价值」的学习点 → 归入知识点（学习主题分两级）→ 大模型出题（先出草稿、确认后才入库）→ 按遗忘曲线排期（默认 SM-2，可选 FSRS-4.5）→ 作答判分并给解析 |
| **场景与策略层** | 通用 / 代码审核 / 文书审核三种场景模板，以及智能体开关策略 | 场景只是「快捷模板」（预置提问话术 + 推荐技能），**审查维度由检查助手按你的任务意图自行确定**，不套固定清单 |

> 名词速记：SSE＝网页与后端之间的「实时消息通道」；REST＝常规的「请求—响应」接口；PoC＝为证明「问题确实能被触发」而实际运行的最小验证程序；SSRF＝诱使服务器去访问内网地址的攻击，本产品对外部链接抓取做了拦截防护；SM-2 / FSRS-4.5＝两种「按遗忘曲线安排复习时间」的算法。

### 3. 产出与复核的职责分离

产品要回答的核心问题是：**谁来审查「审查者」？** 单个 AI 审代码的典型毛病是「说得像真的」——报告写得漂亮，结论却没取过证，于是「审查」退化成了另一份同样需要被审查的 AI 生成物。本产品的解法不是「再加一个 AI」，而是**把「产出」与「复核」拆成职责分离的两段——AI助手 先产出，检查助手 随后独立复核**：

| 维度 | AI助手（执行） | 检查助手（复核） |
|---|---|---|
| 定位 | 台前执行者，它每轮的总结就是你在主界面看到的回答 | 幕后复核者，核查过程与结论显示在任务详情侧栏 |
| 权限 | 完整工具（能写文件 / 跑命令 / 改代码） | **只有只读工具**，没有改代码的权限；也不能再往下派发子智能体（最多一层） |
| 产出时机 | 跑完即标记完成，你拿到结果的时间可预期 | AI助手 完成后在**后台**独立复核一次 |
| 产出内容 | 分析结论、修复建议、（追问轮的）优化计划 | 审查项（按核实结果分三档）、重点与知识点、建议追问方向 |
| 可信来源 | —— | 每条结论都挂靠**非模型产物**：真实源码行 / 验证运行结果 / 抓取到的外部依据；可信度由后端从证据链算出，**模型不得自报数字** |

> 一句话：可信不来自「它是第二个 AI」，而来自**每条结论都挂得住可独立复核的证据**，且**可信度由证据决定，不由模型自己说了算**。

## 二、审查任务工作流

### 1. 全链路：输入 → 分析 → 复核 → 输出 → 出题 → 学习

| 阶段 | 执行者 | 做什么 |
|---|---|---|
| ① 输入 | 用户 | 提交交付物（Git 仓库 / ZIP 压缩包 / 单文件）与任务说明；可选场景模板与执行器 |
| ② 分析 | AI助手 | 按任务说明动手：读源码、跑静态检查、查依赖、执行脚本；需要时可把只读子任务并行拆开做；产出自然语言总结 |
| ③ 复核 | 检查助手 | 后台独立复核一次：**先声明审查计划**（后端自动编号 P1/P2…）→ 只读查证（读源码 / 核实引用 / 跑验证）→ **即时提交结构化审查项** → 按计划编号逐条对账（没取证到的如实标「未核实」，不伪造结论） |
| ④ 输出 | 检查助手 + 后端 | 审查项按三档呈现（已核实成立 / 已核实不成立 / 待核实）；可信度由后端从证据算出；整理「重点与知识点」与「建议追问方向」 |
| ⑤ 出题 | 出题服务 | 对标记了「有出题价值」的学习点，用**本次审查的上下文**（原文段落 / 发现内容）出题；草稿预览、你确认后才入库 |
| ⑥ 学习 | 练习服务 + 用户 | 按遗忘曲线排期推送复习（默认 SM-2，可选 FSRS-4.5）；作答后判分并给解析；知识点看板按学习主题汇总掌握度 |

## 三、典型案例

> 本节案例均取自产品的真实运行记录，非演示脚本虚构

### 案例一 · 代码审查——把 AI 给出的安全结论逐条回源码核实

**用户提交**：本作品自身的源码仓库（GitHub `for-aiedu-student-opc`，相当于拿产品去审自己）。**要求**：审查七类安全风险——注入类（SQL / 命令 / 模板注入）、硬编码凭证与密钥泄露、认证与越权、SSRF、不安全反序列化、配置与依赖风险、敏感信息日志输出，逐条给出具体文件位置、可利用性与修复建议。

**AI助手先给出的结论**：AI助手按五个子任务串行取证，输出一份分级清单——
- 高危 4 条：克隆仓库时把用户可控的地址直接放进命令参数位（没有 `--` 分隔符、不校验协议，可被当作命令行选项利用）；`local` 模式下把模型生成的整条命令交给系统外壳直接执行、命令黑名单闸门容易被绕过，且这条路径不经过原生隔离；登录令牌的签名密钥出厂默认值是固定弱口令，可伪造任意用户；匿名任务对所有登录用户可读可写。
- 中危 8 条：OAuth 登录缺 `state` 校验、用未验证邮箱自动关联账户、文件工具的「仓库根」由模型自己传入导致可读写宿主文件、测试环境校验工具关闭证书校验存在 SSRF、用户自带模型 API Key 明文入库、访问令牌走 URL 查询串传输、命令确认闸门不比对命令 ID、开发模式把完整重置邮件打进日志。
- 低危 10 条：任务参数无字段校验、会话字典并发覆盖、误配即删库、网页服务无 HTTPS 与安全响应头、无鉴权的提示优化接口、无鉴权的调试日志端点、依赖没有锁定版本、前端令牌存本地存储等。
- 另给出正面确认：未发现 SQL 注入、模板注入与不安全反序列化；SSRF 的主路径（外部链接抓取工具）防护完整；日志脱敏、密码与会话、跨站脚本防护、技能与记忆隔离等做法良好。

**检查助手在后台复核**：不照抄结论，先立 5 条审查计划、再回真实源码逐条取证，产出的审查项全部为「已核实成立」：

| 审查项 | 核实结果 | 关键证据（真实源码） |
|---|---|---|
| 克隆仓库时把用户可控地址直接放进命令参数位，无 `--` 分隔、未校验协议 | 已核实成立 · 高 | `sandbox_tools.py:1277` 直接把地址拼进命令参数；以 `-` 开头或 `file://` 的地址会被 git 当作命令行选项解释 |
| `local` 模式下模型命令经系统外壳直跑宿主机，黑名单闸门易绕过且不走原生隔离 | 已核实成立 · 高 | `sandbox_tools.py:3394` 以直接交给系统外壳的方式执行；前置闸门只按 `&&`、`;`、`\|` 三种分隔符切分并匹配固定危险串，`$(...)`、反引号、`find -delete` 不命中即放行 |
| 登录令牌签名密钥出厂默认值为固定弱口令，可伪造任意用户令牌 | 已核实成立 · 高 | `config.py:70` 为普通字符串默认值，签发与校验同用同一对称密钥，全仓没有「非开发环境必须覆盖默认值」的校验 |
| 匿名任务对所有用户可读可写（授权把「无归属」当「无限制」） | 已核实成立 · 高 | `tasks.py:214` 任务列表对登录用户返回「自己的任务 + 匿名任务」；各操作入口只在任务已绑定用户时才校验归属 |
| 文件工具的「仓库根」由模型自己传入，路径穿越防护形同虚设 | 已核实成立 · 高 | `sandbox_tools.py:2077` 穿越校验的比对基准正是模型必填的 `repo_path`；把仓库根传成 `/`、文件路径用相对写法即可读后端任意文件 |
| 命令确认闸门不比对命令 ID，过期的确认可批准另一条命令 | 已核实成立 · 中 | `user_interaction.py:318` 收到 `command_id` 却只在日志里用到，从未与当前待确认命令比对 |
| 用户自带模型 API Key 明文入库，未复用已有的加密存储 | 已核实成立 · 中 | `user_llm_config.py:10` 源码注释自述「API Key 明文存储」，而同仓库对 git 授权令牌用了加密存储 |
| 测试环境校验工具关闭证书校验且不限制目标地址，存在 SSRF | 已核实成立 · 中 | `verifier_tools.py:59` 主动关闭证书校验；该地址入参只有长度限制、没有协议或地址限制 |
| 「无 SQL／模板注入、无不安全反序列化」的正面结论经抽查基本可信 | 已核实成立 · 提示 | `user_git_binding.py:112` 原生 SQL 用占位符绑定参数；全仓未发现不安全的反序列化写法 |

**产出的重点与知识点（7 条，节选）**：
- 有默认值的密钥等于公开的密钥；启动时不校验，生产就一定会沿用；
- 同一仓库里两种加密标准，弱的那条就是漏洞——敏感数据要「一处加密、处处加密」；
- 命令执行防护的三重失效：黑名单闸门挡不住注入、直接交给系统外壳是放大器、「配置里开了隔离」不等于「每条执行路径都真隔离」；
- 外部字符串进命令行参数位：前面补 `--`、拒绝 `-` 开头、限定白名单，三样缺一不可，且只堵主路不够、旁路要另堵；
- 路径穿越防护的「参照物」若由调用方给出，等于没有防护——根必须由服务端固定；
- SSRF 防护三件事缺一不可：拦私网与元数据地址、重定向逐跳复检、保留证书校验；同一能力在不同代码路径防护不一致，弱的那条就是入口；
- 「无归属即无限制」是越权反模式；确认类操作必须绑定「你看到的那一个」对象。

**产出的建议追问方向（3 条）**：补充核查依赖风险（逐条核对前后端依赖清单中各依赖的实际版本是否命中已知漏洞，给出编号与升级建议）；在隔离环境对三个高危项做实际触发验证（默认密钥伪造令牌、匿名任务跨账号操作、测试环境地址指向内网或云元数据）；核查其余可直达宿主机的工具入口（写文件、结构化编辑、跑 Python、切换写入等）是否同样以调用方传入的路径为基准。

### 案例二 · 文书审查——商业计划书的财务与论证

**用户提交**：一份商业计划书（`BP/BP.md`，约 790 行）及其财务附表。**要求**：审核关键假设与数据来源是否可信、市场与竞品论证是否成立、财务模型与单位经济是否自洽、风险与依赖是否充分披露、里程碑与承诺是否可兑现；逐条指出可疑处并说明需补什么证据。

**AI助手先给出的结论**：AI助手完整读取计划书并对全部数字做了勾稽验算，结论先行——「财务模型多处硬性不勾稽、市场论证基本没有可核验的数据支撑、核心定位『功能性心律失常』在临床上不成立、团队不具备经营资质，按现状不具备投资可行性」，随后分五块逐条列出可疑处与原位置：

**产出的重点与知识点（10 条，节选）**：
- 看财务先做三表勾稽：利润表成本总额要和成本预算表对得上，对不上就先找被漏掉的固定支出（通常是房租）；
- 净现值要用自由现金流：含筹资进账的「现金净增加额」不能直接拿来折现，初始投资只能扣一次；
- 「我们没有竞争对手」在计划书里几乎总是伪命题——竞品不是长得像的那个，是抢同一笔预算的那个；
- 市场论证最忌把人口基数当病患基数：市场规模要能由「人群基数 × 患病率 × 可及率 × 支付意愿」逐层推导，并和收入表反推的会员数对得上；
- 数字对了、口径错了，比没数据更危险：「54 万」是心脏性猝死例数，不是「心律失常死亡」；
- 用自造疾病名当市场锚点，整个市场规模就失去可核验基础——没有诊断编码的病撑不起可核验的市场；
- 核数据来源要两步走：先查机构名是否真实存在，再看数字口径有没有被偷换；查不到出处的数字，先当它不存在；
- 单位经济是拆穿「规模幻觉」最快的一刀：把收入按客单价反推成客户数，成本和计划立刻现原形；
- 医疗健康类项目先问牌照再谈增长：执业许可与人员资质必须写进里程碑与预算；
- 医疗类计划书的疗效承诺要备循证依据，否则触碰《广告法》。

**产出的建议追问方向（3 条）**：重新核实计划书正文嵌入的 4 张配图的真实内容，核对图中数字与风险项是否与正文表格一致；按修正后的口径重算一版财务模型（剔除筹资流入与投资收益、把门店租金等全部成本计入损益），给出净现值、内部收益率、投资回收期与首店盈亏平衡点；补充客户侧的实证证据——目标人群对「功能性心律失常康复」的认知度与支付意愿调研，以及医院心脏康复门诊、康复医院、中医馆、在线问诊等替代方各自的价格与服务范围。
