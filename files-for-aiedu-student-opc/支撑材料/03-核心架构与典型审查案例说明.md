# 03 · 核心架构与典型审查案例说明

> 面向非技术背景评委：本文尽量用大白话讲清「谁在做事、结果凭什么可信」。专有名词首次出现时附一句通俗解释。

## 一、系统总体架构

### 1. 总体架构图

```text
              ┌───────────────────────────────────────────────────────────┐
              │                      网页前端（Vue 3）                      │
              │  建任务 / 任务详情（主对话流 + 检查助手侧栏）/ 知识点看板 / 设置  │
              └───────────────▲──────────────────────────┬────────────────┘
                              │ 实时事件流（SSE）           │ 常规接口（REST）
              ┌───────────────┴──────────────────────────▼────────────────┐
              │                  后端服务（FastAPI · 单 worker）            │
              │                                                           │
  交付物 ───► │  编排层：把「先产出」与「后台复核」串成一条流水线               │
              │     ├─ 执行层                                                 │
              │     │    ├─ 内置 AI助手（react_agent）                        │
              │     │    └─ 外部命令行智能体：Qoder / DeepSeek Harness / Codex │
              │     ├─ 检查助手：后台独立复核，只审不改                          │
              │     │    ├─ 只读查证（读文件 / 搜代码 / 列目录）                 │
              │     │    ├─ 引用核实（抓取外部链接，防内网穿透）                  │
              │     │    ├─ 证据台账（结论挂靠真实证据，可信度由后端算）           │
              │     │    └─（实验性）沙箱内实际运行验证                          │
              │     └─ 出题与练习服务（生成 → 确认 → 排期 → 判分）                │
              │                                                           │
              │  工具层 / 证据层 / 智能体策略 / 记忆与场景模板                   │
              └───────────────┬───────────────────────────────────────────┘
                              │ 工具调用
              ┌───────────────▼──────────────────────────────────────────┐
              │     容器化沙箱（OpenSandbox）：隔离执行，克隆仓库、跑验证代码    │
              └──────────────────────────────────────────────────────────┘
```

> 一句话读懂：最上面是网页界面；中间是后端，把「干活」和「复查」排成一条流水线；最下面是隔离的容器沙箱——智能体每一步操作都在沙箱里完成，不影响你自己的电脑。

### 2. 核心模块说明

| 模块 | 职责（大白话） | 关键机制 |
|---|---|---|
| **编排层（总调度）** | 把「先产出」和「后台复查」串成一条流水线：AI助手 先跑 1 轮 → 先给出结果并显示任务完成 → 同一个后台流程接着跑检查助手复查 → 再用提炼出的知识点更新结果 | 网页通过一条常开的实时消息通道接收进度，直到最后一步结束才关闭；用户看到「完成」以 AI助手 结束为准，等待时间可预期 |
| **AI助手（执行者）** | 按你写的任务说明实际动手：克隆仓库、读源码、跑静态检查、执行脚本、写出产物 | 内置实现 `react_agent`，采用「想一步 → 调一个工具 → 看结果 → 再想下一步」的循环（业界称 ReAct）；也可换成外部命令行智能体（Qoder / DeepSeek / Codex）。两者经统一接入协议接入，可随时更换，换执行层不改业务主干 |
| **检查助手（复核者）** | 在后台**先核查、只审不改**：回到真实源码逐条比对、抽查外部引用是否可信、必要时实际跑一段验证代码，最后整理「重点与知识点」与「建议追问方向」 | 通过四个结构化的上报入口即时提交：审查计划 / 审查项 / 知识点 / 建议；每条结论挂靠真实证据（源码行 / 验证运行结果 / 抓取到的外部依据），可信度由后端按证据计算，**模型自己不能报数字**；它没有改代码的权限，只有查证的职责 |
| **工具层** | 智能体伸手要用的各种工具，只负责查证与分析 | 读文件、搜代码、按文件名查找、运行静态扫描（Semgrep / lint）、查依赖漏洞、核实外部引用、在沙箱内跑 Python 或发网络请求等 |
| **容器化沙箱（OpenSandbox）** | 所有工具调用都在隔离的容器里执行 | 自建运行镜像（含 git、ripgrep、python3、Node.js）；验证代码在沙箱内真实触发 |
| **出题与练习服务** | 把真实发现变成练习题 | 标记「有出题价值」的学习点 → 归入知识点（学习主题分两级）→ 大模型出题（先出草稿、确认后才入库）→ 按遗忘曲线排期（默认 SM-2，可选 FSRS-4.5）→ 作答判分并给解析 |
| **场景与策略层** | 通用 / 代码审核 / 文书审核三种场景模板，以及智能体开关策略 | 场景只是「快捷模板」（预置提问话术 + 推荐技能），**审查维度由检查助手按你的任务意图自行确定**，不套固定清单 |

> 名词速记：SSE＝网页与后端之间的「实时消息通道」；REST＝常规的「请求—响应」接口；PoC＝为证明「问题确实能被触发」而实际运行的最小验证程序；SSRF＝诱使服务器去访问内网地址的攻击，本产品对外部链接抓取做了拦截防护；SM-2 / FSRS-4.5＝两种「按遗忘曲线安排复习时间」的算法。

### 3. 产出与复核的职责分离

产品要回答的核心问题是：**谁来审查「审查者」？** 单个 AI 审代码的典型毛病是「说得像真的」——报告写得漂亮，结论却没取过证，于是「审查」退化成了另一份同样需要被审查的 AI 生成物。本产品的解法不是「再加一个 AI」，而是**把「产出」与「复核」拆成职责分离的两段——AI助手 先产出，检查助手 随后独立复核**：

| 维度 | AI助手（执行） | 检查助手（复核） |
|---|---|---|
| 定位 | 台前执行者，它每轮的总结就是你在主界面看到的回答 | 幕后复核者，核查过程与结论显示在任务详情侧栏 |
| 权限 | 完整工具（能写文件 / 跑命令 / 改代码） | **只有只读工具**，没有改代码的权限；也不能再往下派发子智能体（最多一层） |
| 产出时机 | 跑完即标记完成，你拿到结果的时间可预期 | AI助手 完成后在**后台**独立复核一次 |
| 产出内容 | 分析结论、修复建议、（追问轮的）优化计划 | 审查项（按核实结果分三档）、重点与知识点、建议追问方向 |
| 可信来源 | —— | 每条结论都挂靠**非模型产物**：真实源码行 / 验证运行结果 / 抓取到的外部依据；可信度由后端从证据链算出，**模型不得自报数字** |

> 一句话：可信不来自「它是第二个 AI」，而来自**每条结论都挂得住可独立复核的证据**，且**可信度由证据决定，不由模型自己说了算**。

## 二、审查任务工作流

### 1. 全链路：输入 → 分析 → 复核 → 输出 → 出题 → 学习

| 阶段 | 执行者 | 做什么 |
|---|---|---|
| ① 输入 | 用户 | 提交交付物（Git 仓库 / ZIP 压缩包 / 单文件）与任务说明；可选场景模板与执行器 |
| ② 分析 | AI助手 | 按任务说明动手：读源码、跑静态检查、查依赖、执行脚本；需要时可把只读子任务并行拆开做；产出自然语言总结 |
| ③ 复核 | 检查助手 | 后台独立复核一次：**先声明审查计划**（后端自动编号 P1/P2…）→ 只读查证（读源码 / 核实引用 / 跑验证）→ **即时提交结构化审查项** → 按计划编号逐条对账（没取证到的如实标「未核实」，不伪造结论） |
| ④ 输出 | 检查助手 + 后端 | 审查项按三档呈现（已核实成立 / 已核实不成立 / 待核实）；可信度由后端从证据算出；整理「重点与知识点」与「建议追问方向」 |
| ⑤ 出题 | 出题服务 | 对标记了「有出题价值」的学习点，用**本次审查的上下文**（原文段落 / 发现内容）出题；草稿预览、你确认后才入库 |
| ⑥ 学习 | 练习服务 + 用户 | 按遗忘曲线排期推送复习（默认 SM-2，可选 FSRS-4.5）；作答后判分并给解析；知识点看板按学习主题汇总掌握度 |

### 2. 流程图

```text
    用户输入（交付物 + 任务说明）
        │
        ▼
  ┌─────────────────────────────┐
  │  AI助手（执行）              │  完整工具；可按需并行只读子任务
  │  读源码 / 静态检查 / 跑脚本   │

                 │ 自然语言总结
                 ▼
     先落一条临时结果 → 任务标记为「已完成」→ 推送完成事件
        （你已看到「完成」，后台继续）
                 │  同一个后台流程
                 ▼
  ┌─────────────────────────────┐

  └──────────────┬──────────────┘
                 │
        ┌────────┴────────┐
        ▼                 ▼
  建议追问方向         出题服务
  （你一键追问 →          │  「有出题价值」的学习点
   开启新一轮：AI助手        ▼
   再跑一轮 + 后台复查）  知识点看板（学习主题）
                        │
                        ▼
                     大模型出题（取材于你的真实项目）

                        │
                        ▼
                  作答判分 + 解析 → 掌握度回写看板
```

## 三、典型案例

> 本节案例均取自产品的真实运行记录，非演示脚本虚构

### 案例一 · 代码审查——把 AI 给出的安全结论逐条「过堂」

**用户提交**：SecondLook 项目自身的代码仓库（即本作品源码，GitHub 仓库 `for-aiedu-student-opc`，相当于拿产品去审自己）。**要求**：审查七类安全风险（注入类、硬编码凭证与密钥、认证与越权、SSRF、不安全反序列化、配置与依赖风险、敏感信息日志），逐条给出文件位置、可利用性与修复建议。执行层为外部命令行智能体（Qoder）。

**AI助手先给出的结论**：报告共列出 4 条发现，全部落在「注入类」——
- 【高危】默认 local 模式下，智能体工具可在宿主机直接执行代码、危险命令的确认闸门可被低成本绕过（`sandbox_tools.py` 的 `run_python_code`/`run_command` local 分支、`config.py:358` 的 `SANDBOX_MODE` 默认值）；
- 【中危】上传 ZIP 的「解压炸弹」（认为解压总量预算基于可被伪造的文件体积）；
- 一条否定结论：未发现 SQL 注入，`text()` 仅用于启动期写死的 DDL；
- 【低危】ZIP 解压命令拼接漏了引号处理（`sandbox_tools.py:788-794`）。

其余六类风险（硬编码凭证与密钥、认证与越权、SSRF、不安全反序列化、敏感信息日志、依赖风险），报告只在开头以「防护已落地」一句概括，没有逐条结论。
（本轮界面上的审查结论是「4 个维度通过、1 个待改进」。）

**检查助手在后台复核**：它没有照抄，而是先自己立 5 条审查计划（P1–P5），再回到真实源码逐条取证，分档如下：

| 计划 | 核实对象 | 核实分档 | 关键证据（真实源码） |
|---|---|---|---|
| P1 | local 模式下可宿主机执行任意代码、闸门可绕过 | **已核实成立 · 高危** | `config.py:358` 默认 `SANDBOX_MODE=local`；真正的执行入口用 `subprocess.run`、命令用 `shell=True`；安全前缀里含 `python`/`node`，一句 `python3 -c` 即可绕过确认闸门 |
| P2 | ZIP 解压炸弹 | **已核实不成立 · 误报** | 回读解压代码并对照 Python 标准库 `zipfile` 的行为：解压输出受文件头声明的体积约束，「伪造文件头即可无限解压」并不成立 |
| P3 | 「未发现 SQL 注入」 | **已核实成立** | 全仓 `text()` 只出现在数据模型与测试代码里，且插值内容都是启动期写死的常量，外部输入不可控 |
| P4 | 解压命令拼接「属低危」这一定级 | **已核实成立** | 拼接处确实漏了引号处理，但其来源已被清洗、当前不可控，定级低危恰当 |
| P5 | 其余六类风险的覆盖是否到位 | **待核实** | 六类只在报告开头被一句话概括、没有逐条结论，达不到取证的粒度 |

**汇总**：5 条计划全部取证完毕——已核实成立 3 条、已核实不成立 1 条、待核实 1 条。

**一次「补漏」**：核对覆盖度时，检查助手顺着配置读到后端默认签名密钥 `JWT_SECRET` 用了可预测的固定默认值、而生产环境没有任何启动校验（`config.py:70`），判定「部署时忘记修改即可被人伪造登录态」。这条 AI 助手的报告里没有，由检查助手补出并写入结果。

**产出的重点与知识点（6 条，节选）**：
- 默认不隔离的「本地执行模式」，等于把「在宿主机执行任意代码」的风险留在开箱可用状态；
- 命令黑名单防护最容易漏的三处：分隔符没切全、安全前缀被滥用、包装函数没真正被调用；
- ZIP 解压炸弹：伪造文件头其实不管用——一个「看着像漏洞、实为误报」的典型案例；
- `text()` 不等于 SQL 注入，关键看被插值的变量来自哪里；
- 弱默认密钥 + 没有启动校验 = 会「放行」的凭证风险；
- shell 拼接的一致性坏味道：同一函数里有的做了转义、有的没做，往往就是被漏掉的那条路径。

**产出的建议追问方向（3 条）**：补齐「硬编码凭证与默认密钥」的逐条结论（重点即上述默认签名密钥）；逐条核查按 ID 访问的接口是否做了归属校验（防止越权读到他人数据）；对前后端依赖做已知漏洞扫描。

### 案例二 · 文书审查——商业计划书的财务与论证

**用户提交**：一份商业计划书（`BP/BP.md`，约 790 行）。**要求**：核查关键假设与数据来源是否可信、市场与竞品论证是否成立、财务模型与单位经济是否自洽、风险与依赖是否披露充分、里程碑与承诺是否可兑现。执行层为内置 AI助手。

**AI助手先给出的结论**：AI助手通读计划书后逐项指出可疑处，并给出所引原文位置，覆盖财务、市场、数据、里程碑与团队五块——
- 财务自洽：利润表「主营业务成本」与成本预算表对不上（`BP/BP.md:700` / `:429-435`），疑有固定支出漏记；
- 财务模型：净现值与投资回收期测算可疑（`BP/BP.md:759-767` / `:782-790`），结论与表内数据不一致；
- 市场与竞品：市场容量论证不足，把健身房当作最大竞争对手（`BP/BP.md:51` / `:550`）的判断依据不足；
- 数据来源：核心数据所引的「光滑博斯特消费大数据中心」与「每年约 54 万猝死」的引用口径存疑（`BP/BP.md:186` / `:63`、`:77`）；
- 里程碑与团队：阶段年限、市占率目标与团队背景难以支撑其承诺（`BP/BP.md:55` / `:510` / `:524`、`:447-493`）。

（本轮界面上的审查结论是「6 个维度通过、0 个待改进」。）

**检查助手在后台复核**：同样先立 5 条审查计划；因是纯文书、无代码也无测试环境，它由自己逐项取证、不派发并行子流程（这是它按任务性质自行做的判断）。实际产出 6 条审查项，**全部「已核实成立」**：

| 审查项 | 核实分档 | 关键证据（原文行） |
|---|---|---|
| 利润表的成本只算了人力和折旧，门店租金 40 万/年等大项没进表 | 已核实成立 · 高 | 利润表「主营业务成本」恰好等于成本预算表的人力成本加折旧；而成本预算表里另有门店租金 40 万/年、其他费用等整块未进利润表 |
| 净现值把 200 万启动资金扣了两次，回收期结论与表内数据打架 | 已核实成立 · 高 | 折现用的现金流已含当年筹资流入，表里又减一次初始投资；回收期表内累计约 2.18 年转正，文字结论却写约 4.18 年，正文另称「第二年回本」，三处互相矛盾 |

**产出的重点与知识点（5 条）**：
- 审财务先做三表勾稽：利润表的成本总额要和成本预算表对得上，对不上就先找被漏掉的固定支出（通常是房租）；
- 净现值要用自由现金流：含筹资进账的「现金净增加额」不能直接拿来折现，初始投资只能扣一次；
- 市场论证的三大硬伤：没有市场规模拆解、人群数量相加、竞品找错（要找抢同一笔钱的，而不是长得像的）；
- 核数据来源要两步走：先查机构名是否真实存在，再看数字口径有没有被偷换；
- 医疗类项目先看准入资质：执业许可与人员资质是前置硬门槛。

**产出的建议追问方向（3 条）**：重新核实计划书里那 4 张配图的真实内容；按文中公布的定价反推每年需要多少付费客户，并结合单店「1 名医师 + 1 名护士 + 2 名治疗师」的产能，判断收入目标到底做不做得出来；查证三甲医院心脏康复的实际收费与医保，判断「更专业又更便宜」的定位能否成立。
