## 一、系统总体架构

### 1. 总体架构图

```
              ┌──────────────────────────────────────────────────────────┐
              │                        前端 (Vue 3)                       │
              │   任务创建 / 任务详情（主对话流 / 检查助手侧栏）/ 知识点看板 / 设置 │
              └───────────────▲──────────────────────────┬───────────────┘
                              │ SSE 实时事件流            │ REST API
              ┌───────────────┴──────────────────────────▼───────────────┐
              │                   后端 (FastAPI · 单 worker)              │
              │                                                          │
  交付物 ───► │  orchestrator（执行 + 后台质检 串行流水线编排）              │
              │     ├─ 执行器抽象层（ACP 协议）                            │
              │     │    ├─ 内置 AI助手  react_agent（ReAct 循环）          │
              │     │    └─ 外部 CLI：Qoder / DeepSeek Harness / Codex      │
              │     ├─ 检查助手  agent2（后台单次完整审查，核查优先、只审不改）  │
              │     │    ├─ 只读取证（read_file / search_code / list_files） │
              │     │    ├─ 引用复核（check_reference，SSRF 防护抓取）        │
              │     │    ├─ 证据台账 + 置信度派生（evidence.py，模型不自报）    │
              │     │    └─ （实验性）PoC 动态验证 verifier_agent            │
              │     └─ 出题与练习服务（practice：生成 → 确认 → 排期 → 判分）    │
              │                                                          │
              │  工具层  /  证据层  /  智能体策略  /  记忆与场景模板          │
              └───────────────┬──────────────────────────────────────────┘
                              │ 工具调用
              ┌───────────────▼──────────────────────────────────────────┐
              │        OpenSandbox 容器化沙箱（隔离执行；clone / 跑 PoC）    │
              └──────────────────────────────────────────────────────────┘
```

### 2. 核心模块说明

| 模块 | 职责 | 关键机制 |
|---|---|---|
| **编排层 orchestrator** | 把「执行」与「后台质检」串成一条流水线：AI助手 跑 1 轮 → 落临时结果并标任务完成 → 同一后台线程继续跑检查助手审查 → 用知识点替换临时结果 | 事件总线（SSE）保持打开直到最后活跃流收尾；用户感知的“任务完成”以 AI助手 结束为准，保证等待时间可预期 |
| **AI助手（agent1）** | 按用户任务描述实际执行：克隆仓库、读源码、静态检查、跑脚本、写产物 | 内置 `react_agent`（ReAct 循环）或外部 CLI（Qoder / DeepSeek / Codex），经 ACP 协议统一接入；可插拔，换执行层不改业务主干 |
| **检查助手（agent2）** | 后台**核查优先、只审不改**：读真实源码核实、抽查外部引用、必要时生成 PoC，整理“重点与知识点”与“建议追问方向” | 四个结构化发射工具（计划 / 审查项 / 知识点 / 建议）+ 证据台账 + 置信度后端派生；被剥夺改码权限，只有取证职责 |
| **证据层 evidence.py** | 为每条审查结论做引用核验与置信度派生 | 分配 `E1/E2…` 证据引用号；核验 `call_ref` 是否命中本轮真实取证记录、`quote` 是否与读到的正文吻合；分四档置信 |
| **工具层** | 取证与分析的原语 | `read_file/search_code/list_files/find_files`、`run_semgrep/run_lint`、`query_cve/list_dependencies`、`check_reference`、`run_python_code/http_request` 等 |
| **沙箱层 OpenSandbox** | 所有工具调用在容器内隔离执行 | 自建含 git / ripgrep / python3 / Node.js 的运行镜像；PoC 在沙箱内真实触发 |
| **出题与练习服务 practice** | 把真实发现转成练习 | `practice_worthy` 标记 → 知识点（主题两级结构）→ LLM 出题（draft 预览确认后入库）→ 遗忘曲线排期（SM-2，可选 FSRS-4.5）→ 作答判分与解析 |
| **场景与策略层** | 通用 / 代码审核 / 文书审核三场景模板；智能体策略开关 | 场景仅作快捷模板（预设提示词 + 推荐技能），**审查维度由检查助手按任务意图自行确定** |

### 3. 双智能体职责分离说明

产品要回答的核心问题是：**谁来审查“审查者”？** 单个 AI 审代码的典型失效模式是「说得像真的」——报告写得漂亮，结论却没取过证，于是“审查”退化成另一份需要被审查的 AI 生成物。应对不是“再加一个 AI”，而是**把生成与验证拆成职责分离的两个智能体**：

| 维度 | AI助手（agent1，执行） | 检查助手（agent2，质检） |
|---|---|---|
| 定位 | 台前执行者，其每轮总结即用户在主界面看到的回答 | 幕后质检官，核查过程与结论呈现在任务详情侧栏 |
| 权限 | 完整工具集（含写文件 / 跑命令 / 改代码） | **只读工具**，被剥夺改码权限；无法再派发（派生深度 = 1） |
| 产出时机 | 跑完即标记完成，用户拿到结果时间可预期 | AI助手 完成后在**后台**单次完整审查 |
| 产出内容 | 分析结论、修复建议、（追问轮）优化计划 | 审查项（按核实结果三分档）、重点与知识点、建议追问方向 |
| 可信来源 | —— | 每条结论挂靠**非模型产物**：真实源码行 / PoC 运行结果 / 抓到外部依据；置信度由后端从证据链派生，**模型不得自报数字** |

> 一句话：可信不来自“它是第二个 AI”，而来自**每条结论都挂靠可独立复核的证据**，且**置信度由证据链决定、不由语言模型口报**。

## 二、审查任务工作流

### 1. 全链路：输入 → 分析 → 质检 → 输出 → 出题 → 学习

| 阶段 | 执行者 | 做什么 |
|---|---|---|
| ① 输入 | 用户 | 提交交付物（Git 仓库 / ZIP 压缩包 / 单文件）与任务说明；可选场景模板与执行器 |
| ② 分析 | AI助手（agent1） | 按任务描述执行：读源码、静态检查、查依赖、跑脚本；可按需派发并行只读子任务；产出自然语言总结 |
| ③ 质检 | 检查助手（agent2） | 后台单次完整审查：**先声明审查计划**（后端编号 P1/P2…）→ 只读取证核实（读源码 / 查引用 / 跑 PoC）→ **即时发射结构化审查项** → 按计划编号**对账** |
| ④ 输出 | 检查助手 + 后端 | 审查项按三分档呈现（已核实成立 / 已核实不成立 / 待核实）；置信度由后端从证据派生；整理“重点与知识点”与“建议追问方向” |
| ⑤ 出题 | 出题服务（practice） | 对标记 `practice_worthy` 的学习点，用**本次审查的上下文**（原文段落 / 发现内容）生成练习题；草稿预览确认后入库 |
| ⑥ 学习 | 练习服务 + 用户 | 遗忘曲线排期（SM-2，可选 FSRS-4.5）推送复习；作答判分 + 解析；知识点看板按学习主题聚合掌握度 |

```

                 │ 自然语言总结
```

## 三、典型案例一：代码审查

**场景**：提交一个学生用 AI 生成的小程序后端仓库，输入审查维度后发起任务。审查中围绕「安全性 / 依赖风险 / 隐性成本 / 可维护性」展开。（案例为示意，机制为产品真实行为。）

### 1. 问题发现

AI助手 逐文件读源码、扫描依赖清单后给出初步发现（示例）：

- **F1（安全）**：`backend/app/config.py` 中存在硬编码的默认密钥，随仓库提交。
- **F2（依赖风险）**：`requirements.txt` 中某个依赖版本命中公开的高危漏洞（如 PyYAML 早期版本的任意代码执行）。
- **F3（隐性成本）**：一处“无限重试且无退避”的循环调用付费外部 API，存在失控烧钱风险（AI助手初始判断，尚待取证）。

### 2. 证据链

检查助手不采信“口说”，而是**回到真实源码与外部依据逐条取证**，每条结论都挂靠非模型产物：

| 发现 | 取证动作 | 证据（挂靠的非模型产物） |
|---|---|---|
| F1 | `search_code` 命中 → `read_file` 读取原文 | 引用 `config.py:42` 原文行 + 证据台账引用号 `E1`（`call_ref` 指向本次真实读取） |
| F2 | `list_dependencies` 拿清单 → `query_cve` 查该包版本 | 依赖清单条目 + OSV/CVE 记录（`ref_url` + `ref_status=ok` + 权威性判定） |
| F3 | `read_file` 定位循环体 | 源码片段；因缺靶场无法实际触发 → 详见下节“验证状态” |

### 3. 可信度分级（后端从证据链派生，模型不自报）

| 档位 | 含义 | 本案例归属 |
|---|---|---|
| **已动态验证** `verified` | PoC 在沙箱内真实触发且得到定论 | 需 `test_env_url` 靶场，本案例未触发 → 不落此档 |
| **源码取证** `source_confirmed` | 引用命中本轮真实取证记录且 `quote` 与正文吻合 | **F1**（`config.py:42` 原文吻合） |
| **外部佐证** `reference_corroborated` | 引用的外部依据抓取成功且来源权威、可信 | **F2**（CVE 记录佐证） |
| **仅断言·待核实** `assertion_only` | 引用缺失或核验未通过 | **F3**（初始判断未取证前） |

> 机制要点：`quote` 经归一化（剥行号、折叠空白）后做宽松子串匹配；若引用对不上本轮取证记录，置信**自动下调为“仅断言·待核实”**，而不是被“圆过去”。

### 4. 验证状态

每条审查项按核实结果归入三档（后端枚举 `established / not_established / pending_verify`）：

- **F1** → **已核实成立**：源码可指认、引用吻合，`severity` 进入严重度分组。
- **F2** → **已核实成立**（依赖确实存在漏洞版本）：附外部佐证。
- **F3** → **待核实**：缺可访问靶场，PoC 未定论（“试过了但没验出来”），系统**如实标为待核实**并说明原因，不伪造成一条“缺口”结论。

### 5. 学习转化

- F1 标记 `practice_worthy` → 生成知识点「敏感信息不应硬编码进仓库」（含 `learning_note` 讲解），归入学习主题（安全）。
- **真实材料题**：引用回 `config.py` 的原文片段并带上出处；**改编题**：把同一问题形态换进一套全新虚构场景，考察知识迁移。
- 题目 `draft` 预览、答案与解析一并给出，确认后入库 → 按遗忘曲线排期 → 作答判分与解析。

## 四、典型案例二：文书 / 合同审查

**场景**：上传一份大学生创业赛商业计划书（BP），发起文书审查任务。该案例取自演示视频中实际录制的审查任务。

### 1. 条款/内容问题

AI助手 提取 BP 全文后逐板块分析，总体判断为：作为初稿结构完整、板块齐全，服务设计部分能看出确实查过资料；但作为要说服投资人/评委的正式计划书，**财务与合规两条腿站不住**，且硬伤出在最不该出现的位置——

- 专业术语使用有误（行业/医疗相关表述错误）；
- 三张财务报表之间数据互相矛盾；
- 关键合规表述缺失或不当。

### 2. 原文定位

BP 以单文件上传方式进入沙箱工作区，检查助手用只读工具**回到原文**核对，逐条定位到具体段落/表格，引用原文片段作为证据（`call_ref` 指向本次真实读取），而不是凭记忆复述。

### 3. 风险解释

每条问题用大白话讲清“为什么是坑、有什么后果”，支撑当下决策——例如“三表勾稽不上，投资人尽调时第一眼就会怀疑数据真实性；即使内容属实也会被判为不专业”。

### 4. 修改建议

给出可执行的修改方向（改为正确术语、对齐三表数据、补足合规表述），并对无法自行确认的点转为“建议追问方向”，由用户一键追问触发新一轮。

### 5. 学习转化

- 将“财务三表勾稽关系”“行业术语准确性”等标记为学习点 → 知识点看板（学习主题：合同/文书）。
- 出题服务以**本次 BP 的上下文**出题：真实材料题引用回原文段落；改编题换进另一份虚构材料，考察能否独立识别同类问题。
- 由此，审查一个 BP 的过程本身产出一套只属于该用户的学习素材——这是与一切通用刷题工具最根本的结构差异。

## 五、典型案例三：复核纠偏案例

**场景**：展示“执行”与“质检”分离后，检查助手如何**修正 AI助手 的初判**、剔除误报，并**如实处理不确定性**。（案例为示意，机制为产品真实行为。）

### 1. AI助手初判

AI助手 在一轮分析中断言：`/api/export` 接口存在 SQL 注入风险，理由是“看到查询语句与用户输入拼在一起”。这是一条**尚未取证的断言**——若直接写进报告，用户无法分辨真假。

### 2. 检查助手复核后修正

检查助手把该结论作为一条**待核实对象**，回源码取证：

- `search_code` 定位该接口实现 → `read_file` 读取原文；
- 结果发现实际执行的是**参数化查询 / ORM**，用户输入并未拼接进 SQL；
- 于是该审查项判定为 **已核实不成立**（误报剔除），并给出源码依据。

同时，对另一条“疑似越权读取”的结论：检查助手尝试取证但未能读到决定性代码（如权限校验在另一服务中），于是**不硬判**，标为 **待核实** 并写“初步判断…但未独立读取源码确认”的语气。

### 3. 最终报告如何处理不确定性

产品的“诚实”体现在结构与口径上，而非一句承诺：

| 机制 | 作用 |
|---|---|
| **三分档核实** | 已核实成立 / 已核实不成立 / 待核实；**没取到证就不算成立**，存疑一律进“待核实” |
| **置信度后端派生** | 置信档位是**证据链的属性**，不是模型的“口报”；模型不得自报 `confidence` |
| **引用核验** | 引用对不上本轮取证记录或 `quote` 不吻合 → 置信**下调为“仅断言·待核实”**，并在卡片上标「⚠ 证据未核验」 |
| **规划对账** | 检查助手先声明的审查计划逐条对账；**未核实到的计划项如实标为「未核实」并附原因**（取证额度用尽 / 未排到），不伪造成结论 |
| **建议追问兜底** | 确属缺失且无法自查的方向，输出为“建议追问方向”，交用户一键触发，**能自查的绝不建议** |
| **优雅降级** | 无工作区 / 无 PoC 环境 / 引用复核关闭时，对应档位按既定口径降级，不因“没跑成”而谎报或判罚 |

> 结果：同一条初始断言，可能被“证成”“证伪”或“如实存疑”。用户顺着证据可独立复核，「审查」才没有退化成另一份需要被审查的生成物。

## 六、价值总结

### 1. 提升审查可信度

- **每条结论挂靠非模型产物**：真实源码行、PoC 运行结果、抓取到的外部依据（CVE / 安全公告 / 官方文档）。
- **置信度由证据链派生**：把校准置信度的权力从语言模型手里收回，交给“这条结论到底取没取过证”。
- **执行与质检职责分离**：执行者可以“说得漂亮”，但把关者只认证据；误报被剔除，缺口被如实标注。

### 2. 形成“审查—学习”闭环

真实发现 → `practice_worthy` 标记 → 知识点看板（学习主题）→ 用**本次审查上下文**出题 → 遗忘曲线排期 → 作答判分与解析 → 掌握度回写。审查与出题共用一套上下文——**素材同源，不需要通用题库**，这是“审查 + 出题”的架构结果，而非在审查工具上加了个刷题页。

### 3. 服务大学生创业实践

- 让一个大学生个人团队以**接近零边际成本**获得原本只有雇一名技术合伙人才有的验收能力；
- 把 AI 时代最稀缺的能力从“会写”重新定位为“会审”，直接回应“培育适应未来社会的复合型人才”“构建人机协同的教育新生态”；
- 审查 + 出题的组合**不绑定代码**：文书/合同场景以极小成本接入，证明同一架构可迁移到路演、财税等创业任务，支撑“AI Agent 支撑个人或小团队完成创业任务”这一赛道主线。
